# Task 9.3 技术设计

## 边界与依赖方向

监测是可选叶子能力，只依赖稳定项目合同、来源身份、事件库和 Task 9.2 的刷新输入合同；核心项目服务和刷新服务不得反向导入监测模块。这样删除 `skills/_internal/monitoring/` 或不调用监测服务不会破坏新建、打开、恢复和手动刷新。

本任务不实现调度器。宿主未来只需调用监测服务并提交一次来源观察；调度频率、通知渠道和宿主会话属于 Task 9.4。

## 机器合同

新增 `schemas/monitoring-change-candidate.schema.json`，并复制到包内 `src/ci_workflow/schemas/`。候选核心字段：

- `candidate_id`、`project_id`、`contract_version`；
- `source_identity`：来源稳定 ID、来源版本、可复现定位、原始链接；
- `discovered_at` 与追加式 `discoveries`；
- `entity_id`、`claim_domain`、`change_type`；
- `current_value`、`candidate_value`；
- `dedupe_digest`；
- `possibly_affected_reports`、`possibly_affected_page_ids`；
- `acquisition_status`、`diagnostic_status`、恢复尝试与用户指引；
- `user_disposition` 与刷新交接单（如有）。

`dedupe_digest` 从项目、来源身份/版本/定位、实体、声明域、变化类型、当前值和候选值的规范 JSON 计算。来源版本必须是不可变的内容版本，相同内容跨次获取复用同一标识，不能使用抓取时间或运行编号。候选 ID 由该摘要稳定派生。所有公开聚合边界从当前序列化内容重跑完整合同，不信任 `model_copy(update=...)` 后的摘要、状态或交接绑定。

## 持久化与恢复

候选投影写入 `monitoring/inbox/<candidate_id>.json`，使用临时文件加原子替换；文件是当前投影，不是历史真源。完整历史追加到 `events/events.jsonl`：首次发现、重复发现、诊断更新、用户处置和刷新交接分别有稳定事件与幂等键。

加载候选时先根据事件归约出规范投影；文件缺失或漂移时自愈重建。事件摘要、序号或幂等冲突由既有 `EventStore` 失败关闭。不新增数据库表和迁移，避免让可选监测成为核心项目生命周期的强依赖。

## 观察结果与诊断

入口接收调用方已经完成的来源观察，不在应用服务内复制网络抓取逻辑。状态至少区分：

- 已完成并发现变化；
- 已完成但没有变化；
- 来源确认未公开目标信息；
- 技术获取失败，仍可自动恢复；
- 多轮恢复后仍失败，需要用户协助。

技术失败必须记录失败类别、尝试次数、已尝试方法和下一步；未达到恢复次数或未提供已尝试方法时，不得标为“需要用户协助”。无变化观察写事件/回执但不创建空候选。

## 用户处置与刷新交接

候选只允许待处理、启动正常刷新、暂不处理三种用户处置。处置是追加事件，不删除候选。

“启动正常刷新”生成内容寻址的 `MonitoringRefreshHandoff`，绑定候选 ID/摘要、项目 ID、当前合同版本、来源身份和建议复核范围。交接单只是一份刷新输入，不调用 `RefreshService.accept_refresh`、不创建锁定快照、不写报告目录。Task 9.2 在后续正常刷新中仍需重新核验来源、证据门槛、影响图和科学质控。交接单生成后，监测端不再允许改回“暂不处理”；如需停止，由刷新任务处理并保留完整历史。

## 图与 Skill

新增监测节点合同：读取监测范围、执行来源观察、归一化与去重、记录候选/诊断、等待用户处置、生成刷新交接。节点输出不含事实、声明、快照、报告或发布能力。

更新内部监测 Skill，明确候选进入“正常刷新”而非直接进入修订流，并给出四类诊断的中文用户提示边界。

## 兼容与回滚

- `project_service` 现已创建 `monitoring/inbox/`，本任务不改变项目必需文件集合。
- 包清单新增 schema；监测 Skill 保持内部可选能力。
- 若出现候选直接改变科学真源、无用户决定即刷新、监测模块成为核心导入依赖、重复发现制造多候选或技术失败被误报为“未发现”，立即回滚本任务代码，不接入宿主。
