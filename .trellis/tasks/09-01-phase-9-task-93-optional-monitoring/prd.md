# Task 9.3 需求：可选监测与变更候选

## 目标

在支持调度的宿主上，可按既有项目的可变来源范围执行独立监测，将可能发生变化的公开信息写成去重、可追溯、可恢复的变更候选。监测不得改变现行事实、声明、门槛结果、正式快照或报告；只有用户明确选择“启动刷新”后，候选才作为输入交给 Task 9.2 的正常刷新流程重新核验。

## 用户体验

- 用户无需理解调度器、事件流或去重算法；看到的是“发现了什么变化、可能影响哪里、当前能否核验、下一步可做什么”。
- 同一变化被多次发现只保留一个候选身份，同时追加发现和诊断历史，避免重复提醒。
- 网络、登录、限流、页面结构变化等技术失败与“已检索但未发现变化”严格区分；技术问题在穷尽配置的恢复尝试后才要求用户协助。
- 用户可以对候选选择“启动正常刷新”或“暂不处理”。两种处置都追加保存，不覆盖历史。
- 监测 Skill 未安装或被移除时，新建、打开、恢复和手动刷新项目仍正常工作。

## 范围

- §17.3 变更候选 JSON Schema 及 Python 合同。
- `monitoring/inbox/` 中内容寻址、不可覆盖的候选投影，以及 `events/events.jsonl` 中的追加历史。
- 稳定去重摘要、重复发现合并、获取/诊断状态和用户处置。
- 用户明确启动刷新时生成只读刷新交接单；不直接调用刷新接受、快照锁定或报告发布。
- 监测控制图节点合同和内部 Skill 边界更新。
- 合同、集成、异常、恢复和可卸载性测试。

## 不在范围

- 宿主调度器、定时任务界面或 Codex/Hermes/OMP 适配；这些属于 Task 9.4。
- 任何自动接纳事实、自动建立证据/声明/报告快照或自动发布。
- 把候选直接送入修订批准流；候选必须先进入正常刷新并按现行证据门槛重新核验。
- 站点页面、PDF、HTML-PPT、PPTX 或视觉导出。
- 安全专项测试。

## 验收标准

1. 候选合同至少保存候选 ID、来源/版本/定位、发现时间、实体与声明域、变化类型、当前值与候选值、去重摘要、可能影响的报告/页面、获取/诊断状态和用户处置。
2. 相同业务变化的重复发现返回同一候选 ID，并追加发现记录；同一来源但不同定位、版本或候选值形成不同候选。
3. 候选历史不可覆盖；当前投影可由规范事件流确定性重建，投影丢失或漂移时自愈，同一幂等键不同载荷失败关闭。
4. 监测成功但无变化、证据未公开、技术获取失败、需要用户协助四类结果可区分，且中文提示说明阻断原因与用户要做什么。
5. 用户“启动正常刷新”只生成绑定项目、候选和当前合同版本的刷新交接单；不改变事实/声明表，不建立正式快照，不接受子版本，不生成或发布报告。
6. “暂不处理”保留候选及历史，不删除、不改写；处置重放幂等。
7. 移除或不导入监测模块后，项目新建/校验、打开/恢复与 Task 9.2 手动刷新回归继续通过。
8. 聚焦测试、相关历史回归、Ruff、mypy、包完整性和独立复审通过。
