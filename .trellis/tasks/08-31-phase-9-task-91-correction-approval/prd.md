# Task 9.1 需求：来源关联修订与明确批准

## 目标

让用户能从站点报告中的事实、图点、矩阵单元或声明发起修订，但不能直接改写科学真源。系统保存完整建议、核验证据和影响范围，只有用户明确批准且受影响内容重建、独立质控通过后，才发布新版本。

## 用户体验

- 站点可导出一个自包含修订包；不要求用户安装服务或理解数据库字段。
- 用户可见内容只表达：要修订什么、当前显示什么、建议改成什么、理由和补充来源。
- 系统需要补证据时，用自然中文说明缺什么以及用户可提供什么，不展示内部状态名。
- 验证通过仍必须等待用户明确批准；系统不能替用户批准。

## 范围

- `correction-proposal` 机器合同及源码包副本。
- 追加式修订服务：提交、补证、验证处置、用户决定、发布。
- 修订控制图定义与既有状态迁移/守卫复用。
- 新快照、影响集合、重建和独立质控作为发布前条件。
- 同一批准 ID 的发布幂等；历史事件和旧版本不可覆盖。

## 不在范围

- Task 9.2 增量刷新与影响传播执行器。
- Task 9.3 监测候选。
- 三宿主安装、候选包或真实浏览器视觉验收。
- PDF、HTML-PPT、PPTX 生成或导出。

## 验收

1. 六种修订状态与已批准 v1.2 完全一致，所有允许迁移均有事件和守卫证据。
2. `submitted` 可进入需补证据、拒绝或等待用户批准；补证据后可回到提交状态。
3. 验证动作不能写入批准；只有明确的报告所有者决定可进入批准状态。
4. 发布必须同时满足：新快照、受影响内容重建、独立质控通过；缺一项失败关闭。
5. 历史追加保存，重复提交、批准或发布不重复创建版本或产物。
6. 自包含修订包通过 schema，绑定项目、报告、快照、稳定目标 ID、旧值、建议值、理由、来源与影响集合。
7. 相关测试、mypy 和 Ruff 通过；不扩大安全测试。
