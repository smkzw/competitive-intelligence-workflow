# Task 9.1 技术设计

## 边界

修订服务位于应用层，复用现有 SQLite 项目库、事件存储、内容寻址与修订状态迁移合同。它不直接修改事实表、声明表或报告文件；发布只登记新的不可变版本及其关系。

## 数据合同

`CorrectionProposal` 至少包含：建议 ID、项目 ID、报告类型与版本、快照 ID/摘要、目标类型和稳定 ID、当前可见值、建议值或解释、用户理由、提交时间、附件/链接、验证证据、冲突、影响集合、报告所有者决定、发布幂等键和前后版本关系。

面向用户导出的 JSON 不出现内部标签；机器状态保存在合同字段中，由 Agent 转译为中文指引。

## 服务操作

1. `submit`：校验项目与当前快照绑定，保存首次建议和事件。
2. `add_evidence`：向同一建议追加来源，不覆盖原提交。
3. `validate`：记录身份、上下文、定位、冲突和影响核验；结果只能是需补证据、拒绝或等待用户批准。
4. `record_owner_decision`：只接受报告所有者的明确批准、拒绝或要求补证据。
5. `publish`：核验批准 ID、新快照、影响集重建和独立质控，幂等登记新版本；不得修改旧版本。

所有操作通过确定性幂等键抵抗检查点重放。状态转换调用现有 `graph/transitions.py` 与 `graph/guards.py`，不另造一套状态机。

## 持久化与恢复

既有 `correction_proposals` 表保存当前投影；完整操作历史保存为追加事件。若服务在事件写入后崩溃，重放同一幂等键返回既有结果，不重复批准或发布。发布失败保留批准状态和失败原因，等待相同建议恢复，不回写旧快照。

## 兼容性

首版站点式 HTML 只需导出修订包；宿主桥接摄取在 Phase 9.4 完成。当前实现不得依赖网络、PDF/PPT 运行时或前端框架。
