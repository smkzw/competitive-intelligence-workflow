# Task 10.1 产品需求

## 目标

固定首版发布验收的唯一机器可读场景目录。后续 Task 10.2、10.3、10.6、10.8 只能从该目录解析适应症、时区、数据截止、脱敏输入摘要、预期状态、不变量、验证器、责任阶段和回执位置，不能在命令行或 Agent 提示中临场猜测。

## 用户与验收者体验

- 面向用户的首版仍只需选择 A/B/C 报告并输入适应症，输出固定为站点式 HTML。
- catalog 和矩阵说明使用中文临床试验语境；内部状态码可以存在于机器合同，但不得成为报告页面文案。
- 每个异常场景必须区分：资料确实未公开、检索穷尽仍未找到、技术/网络/登录故障、关键证据不足、等待用户补件。
- 负向旧报告只作为失败样本，不得迁移为模板或视觉参考。

## 首版场景

1. A：特应性皮炎完整候选宇宙，成熟、早期、暂停/终止项目并存。
2. B：PNH 疗效、安全性、基线、试验完成/处置及支持证据完整路径。
3. C：登记字段足够通过；关键临床设计字段缺失后经 Protocol/SAP 补件恢复。
4. `full-matrix-v1`：同一脱敏项目生成 A+B+C 三类多页面站点式 HTML；固定适应症、IANA 时区、已物化数据截止和逐文件 SHA-256。
5. 历史截止：区分 cutoff 前披露/后获取与 cutoff 后首次披露，跨日恢复不得漂移。
6. `required-v12`：覆盖创新药范围、研究角色、证据冲突、B/C 关键路径、人工补件、技术恢复、状态重放、康哲站点运行、三宿主、恢复演练、旧根处置和旧版负向回归。

## 范围裁决

ADR 0013 高于原 Task 10.1 四格式措辞：首版 `full-matrix-v1` 的必选格式只有 `html`；不创建或要求 PPTX 八项确认 fixture，不以 PDF、HTML-PPT、PPTX 缺失制造部分交付。原四格式场景和确认合同保留在 Phase 8 检查点，未来恢复时另建扩展 catalog 版本，不能追溯性改变本首版目录。

## 验收标准

1. `fixtures/acceptance/catalog.yaml` 有明确 Schema 版本，并唯一登记 `full-matrix-v1` 与全部 `required-v12` case 族。
2. 每个场景声明稳定 case id、适应症/适用性、`execution_scope`、owner task、逐文件输入摘要、预期状态与不变量、精确测试或 verifier、回执相对路径。
3. `full-matrix-v1` 固定 IANA 时区和带偏移的数据截止；输入包逐文件摘要与 case digest 可重算。
4. 历史截止场景固定披露时间、获取时间和跨日恢复用物化 cutoff。
5. required case 族与批准矩阵双向闭合；缺失、额外无解释、摘要漂移、owner/scope/receipt 缺失均失败关闭。
6. 正向输入来自已脱敏且身份核验的既有 fixture；负向旧输出只以摘要和失败预期引用，不复制进正向模板。
7. `docs/acceptance/matrix.md` 让医学/验收人员一眼看懂每个场景验证什么、何时执行、成功与阻断意味着什么。

## 非目标

- 不运行真实 fresh-source A/B/C 验收，不生成 RC。
- 不实现 PDF、HTML-PPT、PPTX 或四格式覆盖。
- 不执行迁移、切换或删除旧工程。
- 不进行安全专项测试。
